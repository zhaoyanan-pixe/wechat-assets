想象一下：把仓库权限交给一个 AI，三天过去，它一行代码都没提交。

不是坏了。是它故意的。

10 月 31 日，DeepSeek 在 GitHub 上放出一个叫 dsh-superagent 的东西，README 开头就写着：研究原型，不是官方产品。

到今天早上 8 点，13,067 星，1,356 个 fork。满打满算，三天。

仓库页实拍：三天 1.3 万星，97.5% 的代码是 TypeScript（2026-11-03 上午采集）

我把它九篇文档翻完，最想聊的不是它能干什么，而是它默认「不干什么」。

它的第一条原则，是教自己闭嘴

第一篇文档只有三十几行，开头就把原则摊开了：尽量少占用人的注意力，尽量多给价值。

下一段更像记账：一条消息、一个通知、一个问题、一个设置项、面板上的一个格子、文档里的一句话，每一样都在花别人的注意力，那就都得值这个价，不值就删。

大多数工具的心气是「再加一个功能」，它的心气是「再砍一个打扰」。

官方文档 000-philosophy 原页面：核心原则和五条准则就写在这一页

一条消息，怎么变成一张工单

它干活像个很小的公司，分工很清楚。

有人在仓库里提了需求，算一次触发；它先研判，该不该接、能接多宽，一条条对着团队写下的规则判；判过了才开工单，单上记着依据哪条规则、谁提的、权限多大；然后派给一个执行器，在它自己的会话和独立目录里干；干完回到原来那条对话交付，比如直接提个 PR。

官方文档里的分工：触发 → 研判 → 工单 → 执行器 → 回原对话

这套流程最值钱的地方是有据可查。不是「AI 说它做了」，而是这张单子上写着它凭什么做、做到哪一步。

它还有个网页面板，只回答三个问题：现在有没有事需要我？系统健康吗？某一件活从哪来、到哪去。

翻译一下：没事的时候，它不该占你屏幕。

最妙的是中间那个默认档

它能主动接活，但默认停在 observe，观察档。

有人提了个需求，它判断这活自己能干，然后记一笔「本来会接」，一行都不改。等你翻了几十条这样的记录，觉得它判断得对，再手动切到 auto。

名单上的人点名找它，三个档位都照常接。边界也分得很细：名单上的人、名单外的人、点了它名字的、没点名的，一张准入表一格一格写清楚，默认大多从紧，拿不准就不接。

三档接单模式：默认 observe，只记录「本来会接」，不动手

我喜欢这个顺序。先让它证明自己会判断，再让它动手。

我们怕 AI 乱来，怕的从来不是它不会干，是它不打招呼就干了。

它把「不要什么」也写成了文档

文档里我最喜欢的一节不叫功能，叫「被否掉的概念」，十二条，每条都写了为什么不要。

不给人单独建一个实体，人只是消息上的一个署名；不给工单加「等待中」，等待是来源该管的事；规则一变，不取消正在跑的工单，那会留下半截活。

一个项目愿意把删掉的设计摊开给你看，通常说明它想清楚了。

五条行为准则，第一条就把「不许自作主张」写死了

这五条里我最服第三条：一次只问一个具体问题，还用结构化表单问。

平时收到的 AI 汇报，最烦的就是一大段话里藏着一个要你拍板的事，看完还得回头找。

冷水也得泼

第一，这是研究代码。README 自己写得清楚：不是官方产品，可能有 bug，很多代码是 AI 写的，用之前自己审一遍。

第二，装起来不轻松。要一个 DeepSeek Harness 环境、一个专门的 GitHub 机器人账号、一个仓库，最好还有台一直开着的机器。官方让 coding agent 读 SETUP.md 陪你一步步配，一次只问一个问题，很像它自己那套规矩。

第三，它不是给个人玩家准备的。整套授权、工单、派工，是给「一个团队 + 一个仓库」设计的。你一个人写小项目，用不上。

但它值得看。哪怕不装，光是「注意力记账」这个算法，也够你回头审一遍自己那些天天响的机器人通知。

那它适合谁

有开源项目、有一堆 issue 和 PR 要回、团队里总有人被 @ 到烦的那种。

或者像我这样，想让 AI 多干活，又不想它半夜自作主张的人。

它给的答案很朴素：先把权限收到最小，先让它只记录，等你看顺眼了再放手。

AI 靠不靠谱，不取决于它多能干，取决于你给它留了多大的口子。

🧰 上手小抄
① 打开仓库读 SETUP.md，让你的 coding agent 陪装（要 DeepSeek Harness + 一个 GitHub 机器人账号）
② 先别切 auto，留在 observe 档看几天记录，判断准了再放权
③ 这是研究原型，别直接接到公司主力仓库上
